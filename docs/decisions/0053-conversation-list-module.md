# 0053 — 스레드 소속과 대화 목록은 conversations.mjs 한 module이 정하고, 다시 설명한 답은 원래 답의 스레드에 남는다

Date: 2026-10-12
Status: Accepted. 구조 점검 후보 4. ADR 0022 §1과 Consequences, ADR 0038 §5·§6을 한 규칙으로 구현한다.

## Context

1. 어느 문답이 어느 스레드에 속하는지를 세 곳이 따로 정했다. 웹은 "카드가 지금 목록에 없는 스레드의 문답"까지 세션 전체 대화에 모았다. 터미널은 서버가 붙인 `thread`가 같은 문답만 보여 주고, 카드가 없는 스레드는 "[저장 대화]"로 따로 보여 줬다. 서버는 이어 묻기 맥락을 고를 때 질문 대상 내용을 직접 비교했다.
2. 세션 전체 대화에서 설명 방식 메뉴로 다시 설명하면 웹은 직전 답을 질문 대상으로 보냈고, 서버는 그 답 내용의 해시를 스레드로 저장했다. ADR 0022는 이 답이 세션 전체 대화에 남는다고 했지만, 실제로는 새 스레드가 생겼다. 웹은 그 스레드에 카드가 없어서 세션 전체 대화에 보였고, 터미널은 세션 전체 대화에서 빼고 "[저장 대화]"로 따로 보였다. 서버도 이 질문을 세션 전체 대화의 이전 문답 없이 새 대화로 설명했다.
3. 같은 문답이 웹에서는 카드가 최근 목록에 있는지에 따라 다른 스레드에 보였다.
4. 터미널은 서버의 스레드 식별자 계산(`createHash`)과 카드 질문 대상 계산을 복사해 두었고, 웹도 카드 질문 대상과 제목, 줄임 표시(다른 표시 문구)를 따로 만들었다. 서버가 `/api/live` 카드에 이미 `focus`와 `thread`를 붙이므로 이 복사본은 쓰이지 않거나, 쓰이면 다른 키를 만들 수 있었다.
5. 질문과 함께 보내는 카드 목록은 터미널만 걸러 보냈다. 웹은 제목 길이를 자르지 않아 서버가 질문 전체를 400으로 거절할 수 있었다.

## Decision

1. **소속 규칙은 하나다.** 문답은 서버가 붙인 `thread`와 같은 스레드에만 보인다. `""`는 세션 전체 대화다. 카드가 지금 목록에 있는지는 소속을 바꾸지 않는다. 서버의 이어 묻기 맥락(`ask.mjs`), 웹, 터미널이 모두 `app/conversations.mjs`의 `threadRows`/`inThread`를 쓴다.
2. **다시 설명한 답은 원래 답의 스레드에 남는다.** 서버는 문답에 스레드를 붙일 때 질문 대상이 같은 세션의 앞선 답 내용(`answerFocus`: 결론, 설명, 자세히를 이은 글)과 같으면 그 답이 있던 스레드를 쓴다. 아니면 질문 대상 내용의 해시다. 같은 내용의 답이 여러 스레드에 있으면 가장 먼저 나온 답의 스레드다. 그래서 나중 문답이 이미 정한 스레드를 바꾸지 않고, 질문을 열 때 정한 스레드(작업 목록과 답의 `thread`)와 저장 뒤 `history()`가 붙이는 스레드가 같다. 새 질문(`ask.mjs`)과 저장된 문답(`history()`)이 같은 규칙(`thread.mjs`의 `threadOf`/`withThreads`)을 쓴다. 저장 형식은 바꾸지 않으므로 이미 저장된 다시 설명 문답에도 적용된다. 다시 설명은 그 스레드의 살아 있는 대화와 이전 문답을 맥락으로 쓴다.
3. **대화 목록은 한 함수다.** `conversationList(rows, cards)`가 세션 전체 대화, 사건 카드(받은 순서, 같은 스레드는 처음 카드 하나), 카드가 목록에 없는 저장 대화(마지막 문답이 최근인 순)와 각 문답 수를 돌려준다. 터미널 대화 선택(Ctrl+T, `#`)과 웹 세션 전체 대화가 이것으로 그린다.
4. **웹의 카드 없는 저장 대화.** 웹은 세션 전체 대화 맨 위에 "작업 내용에 없는 카드의 저장 대화" 바로가기를 둔다. 누르면 그 스레드의 문답을 열고, 이어 물으면 같은 스레드에 쌓인다. 새 스타일 없이 기존 버튼 모양을 쓴다.
5. **클라이언트는 스레드와 질문 대상을 계산하지 않는다.** 카드는 서버가 붙인 `focus`와 `thread`가 있을 때만 만든다. 터미널의 `threadKey`·`focusForEvent` 복사본과 웹의 대체 계산, 웹의 `blockTitle`·`excerpt` 복사본을 지운다. 중단한 질문을 돌려줄 때 터미널은 보낸 순간의 스레드(서버가 준 값) 또는 `/api/jobs`의 `thread`로 돌아간다.
6. **질문과 함께 보내는 카드 목록은 `cardsPayload`로 정리한다.** 서버가 준 16자리 스레드만, 같은 스레드는 한 번, 제목은 다듬어 200자, 최근 40개다. 서버의 `parseCards`는 그대로 엄격하다.
7. `conversations.mjs`는 `node:` module을 쓰지 않는다. 웹은 `/conversations.mjs` 정적 파일로 불러오고(`mobile.mjs`와 같은 방식, 빌드 없음), 터미널과 서버는 직접 불러온다. 스레드 해시는 서버의 `thread.mjs`에만 있다.

## Consequences

- 세션 전체 대화에서 다시 설명한 답은 웹, 터미널, 서버 맥락 모두에서 세션 전체 대화에 있다. 터미널에 그 답만 담긴 "[저장 대화]"가 더는 생기지 않는다.
- 웹 세션 전체 대화는 카드가 최근 목록에서 빠진 카드 스레드의 문답을 더 이상 섞어 보여 주지 않는다. 대신 맨 위 바로가기로 연다. 카드 목록이 바뀌어도 문답의 자리가 바뀌지 않는다.
- 카드 스레드나 저장 대화 안에서 고른 설명 방식은 원래처럼 그 스레드의 질문 대상을 쓰므로 그 스레드에 남는다.
- 답 내용이 7800자를 넘으면 카드와 같은 줄임 표시로 보낸다. 웹의 용어 풀이 질문은 용어가 200자를 넘을 때 줄임표(…)로 자른다.
- 서버는 질문 대상이 있는 질문을 열 때 그 세션의 문답을 한 번 더 읽는다. 같은 requestId 재요청은 작업 합류나 저장된 답으로 끝나므로 스레드가 바뀌지 않는다.
- 두 스레드에 글자까지 같은 답이 있으면 다시 설명한 답은 더 이른 답의 스레드로 간다. 화면이 어느 답을 다시 설명했는지 보내지 않으므로 서버가 구분할 수 없다. 짧은 정형 답(근거 없음 안내 등)에서만 생길 수 있다.
- 이 결정 전에 웹이 7800자가 넘는 답을 다시 설명해 저장한 문답은 줄임 표시가 달라(`[중간 생략, …]`) 맞춰지지 않는다. 그런 문답은 세션 전체 대화 대신 맨 위 바로가기에서 열린다.
